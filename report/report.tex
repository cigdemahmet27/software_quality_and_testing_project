\begin{abstract}
In this report, we go over the work we did for the BLG~475E Software Quality and Testing term project. We picked two Large Language Models, Gemini Pro (LLM~1) and Claude Opus~4.6 (LLM~2), and tested how well they can write code and generate unit tests for 30 Java tasks from the HumanEval dataset. Since API costs were too high, we used a semi-agentic workflow where we gave prompts through each model's web interface and then put the generated code into our Maven project by hand. Our testing pipeline had three stages: first we ran the base tests and checked branch coverage with JaCoCo, then we asked the LLMs to write better tests to cover missed branches and we ran JNose for test smells, and finally we wrote manual black-box tests using equivalence class partitioning and boundary value analysis. Both LLMs got to 100\% branch coverage after the improvement step. But the manual tests still found 2 bugs in LLM~1's code and 4 bugs in LLM~2's code. In Phase~2, we extended the project with integration testing by creating a \texttt{BookScan} class that combines three HumanEval tasks (\#18 substring counting, \#23 string length, \#27 case flipping) into a text analysis tool. We compared code generated from unmodified (raw) prompts versus edited (engineered) prompts. The edited prompts eliminated most bugs and produced consistent APIs, with the largest improvement seen in Claude (LLM~2). Our test effectiveness analysis showed that despite 95--100\% branch coverage, the LLM-generated tests only covered 39.4\% of systematically identified equivalence classes and boundary values, reinforcing that branch coverage alone is insufficient.
\end{abstract}

\section{Introduction and Literature Review}
\label{sec:introduction}

\subsection{Introduction}

Large Language Models (LLMs) like Google's Gemini and Anthropic's Claude have become popular tools in software development. They can write code from plain English descriptions and they can also generate unit tests, which makes them useful for speeding up the development process.

Writing tests by hand takes a lot of time and effort, and it is easy to miss edge cases. LLMs can help with this by generating test cases from function signatures and docstrings. But the code that LLMs write is not always correct. Research has shown that it can have subtle bugs, especially around boundary conditions and performance~\cite{chatunitest, mutation_meta}.

In this project, we used two LLMs (Gemini Pro and Claude Opus~4.6) to generate Java solutions and tests for 30 tasks from the HumanEval benchmark~\cite{humaneval}. We then checked the quality of both the code and the tests through a multi-step process: base testing, coverage-driven test improvement, test smell detection, manual black-box testing with equivalence classes and boundary values, and finally LLM-assisted bug fixing.

\subsection{Literature Review}
This section reviews five recent studies that investigate the use of LLMs in automated test generation and code quality assurance.

\subsubsection{ChatUniTest: A Framework for LLM-Based Test Generation}
Chen et al.~\cite{chatunitest} present \textit{ChatUniTest}, an automated unit test generation framework that addresses two key weaknesses of LLM-based tools: limited context windows and insufficient validation of generated tests. The framework introduces an \textit{adaptive focal context} mechanism that extracts only the relevant method, class properties, and dependencies via AST parsing, rather than feeding the entire source file to the model. Generated tests pass through a Generation-Validation-Repair cycle that includes syntactic, compilation, and runtime checks, with both rule-based and LLM-based repair strategies. In evaluation, ChatUniTest achieved 59.6\% line coverage, outperforming TestSpark (42.1\%) and EvoSuite (38.2\%). This paper is directly relevant to our project since our workflow similarly relies on iterative prompt construction and post-generation validation to obtain compilable and correct unit tests from LLMs.

\subsubsection{Mutation-Guided LLM-Based Test Generation at Meta}
Foster et al.~\cite{mutation_meta} describe Meta's \textit{Automated Compliance Hardening (ACH)} system, which combines mutation testing with LLM-based test generation. Rather than prompting an LLM to ``write tests'' generically, ACH first generates targeted mutants (simulated faults specific to a concern such as privacy) and then instructs the LLM to produce tests that kill these mutants. Deployed on 10,795 Kotlin classes across seven Meta platforms, ACH generated 571 hardening test cases with a 73\% developer acceptance rate. A notable finding is that 49\% of the valuable tests did not increase line coverage, demonstrating that coverage alone is an insufficient quality metric. This insight directly informs our manual assessment phase, where we complement coverage analysis with equivalence class partitioning and boundary testing.

\subsubsection{Adaptive Testing for LLM-Based Applications}
Yoon et al.~\cite{adaptive_testing} address the challenge of efficiently testing LLM-powered applications by adapting \textit{Adaptive Random Testing (ART)} to text-based prompt templates. Their approach iteratively selects the most diverse candidate input (measured via string distance metrics such as Levenshtein and Jaccard) and dynamically adjusts selection based on prior pass/fail outcomes. The technique discovers failures significantly faster than random sampling while requiring fewer costly API calls. For our project, this work provides a theoretical foundation for the input diversity strategies we apply when designing equivalence classes and selecting varied test inputs from the HumanEval dataset.

\subsubsection{LLM-Based Code Generation for Golang Compiler Testing}
Gu et al.~\cite{golang_compiler} investigate using LLMs as intelligent fuzzers for compiler testing. By fine-tuning an LLM on a carefully filtered Go codebase and guiding generation with a coverage-based seed scheduling strategy, the authors achieved 3.38\% compiler code coverage. This is nearly eight times higher than standard Go fuzzing (0.44\%). The generated code exhibited only 2.79\% syntax errors and effectively zero undefined behaviors. Although our project targets Java unit tests rather than compiler fuzzing, this paper demonstrates how constrained, seed-guided LLM generation can produce high-quality code artifacts, reinforcing the value of prompt engineering and structured generation strategies in our own pipeline.

\subsubsection{LLM-Based Test-Driven Interactive Code Generation}
Fakhoury et al.~\cite{ticoder} propose \textit{TiCoder}, an interactive workflow where the LLM first generates unit tests from a natural language prompt to formalize user intent, and then produces the implementation code constrained by those tests. In a user study with 15 programmers, participants using TiCoder were significantly more likely to correctly evaluate AI-generated code and reported lower cognitive load. At scale, the approach improved pass@1 accuracy by approximately 46\% within five interaction rounds. This paper is highly relevant to our project: it validates the test-driven philosophy we adopt in Phase~1, where LLM-generated tests serve as the specification against which code correctness is evaluated, and it motivates the iterative refinement approach we use in both our agentic and semi-agentic workflows.

\subsection{Semi-Agentic Approach Justification}
At first, we tried to build a fully automated pipeline using Python scripts that would call the models' APIs directly. But we ran into problems with API rate limits and token quotas. The free tiers ran out fast when dealing with 30 tasks, and paying for more was not an option.

So we switched to a \textit{semi-agentic approach} instead. We wrote the prompts on our machines, pasted them into each LLM's web interface, and then copied the generated code back into our Maven project by hand.

\subsection{Advantages and Limitations}
This approach had some clear pros and cons.

\textbf{Advantages:}
\begin{itemize}
    \item \textit{No cost:} Using the web interface meant we did not have to pay anything or worry about token limits.
    \item \textit{More control:} We could see exactly what the model was doing at each step and fix our prompts if something went wrong.
\end{itemize}

\textbf{Limitations:}
\begin{itemize}
    \item \textit{Lots of manual work:} Copying and pasting code for 30 tasks across two models took a long time.
    \item \textit{Not scalable:} This would not work well for the full HumanEval dataset (164 tasks) or for a CI/CD pipeline.
\end{itemize}

We picked 30 prompts from the HumanEval dataset~\cite{humaneval}. 
The full list can be found in \texttt{dataset/selected\_prompts.json}. 
Our selection criteria were:

\begin{itemize}
    \item \textbf{Difficulty mix:} 15 easy, 10 moderate, and 5 hard prompts so we could test the LLMs at different complexity levels.

    \item \textbf{How we classified difficulty:} Easy tasks have simple logic and few edge cases. Moderate tasks need multiple steps or careful handling of special inputs. Hard tasks involve recursion, complex math, or tricky algorithms.
\end{itemize}

\subsection{Coverage Discussion and Input Mutations}

Our manual tests covered all the equivalence classes and boundary conditions we identified. We ran 273 tests per LLM and the results are documented in \texttt{analysis/manual\_test\_reports/}.

\textbf{LLM~1:} 271 out of 273 tests passed (99.3\%). The two failures were:
\begin{itemize}
    \item Task~\#31 (\texttt{isPrime}): The loop condition \texttt{i * i <= n} causes integer overflow when testing \texttt{Integer.MAX\_VALUE}.
    \item Task~\#45 (\texttt{triangleArea}): The multiplication \texttt{a * h} overflows to infinity when \texttt{a = Double.MAX\_VALUE}.
\end{itemize}

\textbf{LLM~2:} 269 out of 273 tests passed (98.5\%), with 3 failures and 1 timeout:
\begin{itemize}
    \item Task~\#13 (\texttt{greatestCommonDivisor}): Does not handle negative inputs and returns a negative GCD.
    \item Task~\#25 (\texttt{factorize}): The $O(n)$ loop times out on a large prime (about 2.1 billion iterations).
    \item Task~\#45 (\texttt{triangleArea}): Same overflow problem as LLM~1.
    \item Task~\#49 (\texttt{modp}): Returns 1 instead of 0 when $n=0$ and $p=1$ because the initial value is not reduced by modulo.
\end{itemize}

This shows something important: even though both LLMs got 100\% branch coverage, that was not enough to catch these bugs. The buggy code paths were technically ``covered'' but nobody tested them with extreme values. This matches what Foster et al.~\cite{mutation_meta} found, which is that 49\% of useful tests did not increase line coverage at all.

We did not need to create input mutations because the boundary values we picked by hand were enough to find all the bugs.

\subsection{Statistical Evaluation}

Both LLMs wrote code that works fine for normal inputs---all 30 tasks passed the base and improved tests with a 100\% pass rate. The bugs only showed up when we ran the manual boundary tests. So both models are good at handling common cases but they have trouble with extreme inputs.

Some things worth noting:
\begin{itemize}
    \item \textbf{Bug rate:} LLM~1 had bugs in 2 out of 30 tasks (6.7\%), and LLM~2 had bugs in 4 out of 30 tasks (13.3\%). So LLM~1 wrote more reliable code when it comes to edge cases.
    \item \textbf{Types of bugs:} LLM~1 only had overflow problems (integer and double). LLM~2 had a wider mix---missing input checks, a slow algorithm, and a wrong initial value.
    \item \textbf{Same bug in both:} Task~\#45 (\texttt{triangleArea}) was broken in both LLMs. They both wrote \texttt{a * h / 2.0} without thinking about what happens when \texttt{a} is very large.
    \item \textbf{Coverage is not enough:} All tasks had 100\% branch coverage, but 6 bugs were still hiding in the code. This proves that coverage alone does not mean the code is correct.
\end{itemize}

\subsection{Refactoring Process}

Once we found the bugs through manual testing, we used the LLMs to fix them. The prompts and responses for each fix are saved in \texttt{llm\_logs/llm1/refactoring/} and \texttt{llm\_logs/llm2/refactoring/}. Here is how we did it:

\begin{enumerate}
    \item We looked at the failing test to understand what went wrong and why.
    \item We wrote a prompt that included the buggy code, the failing test, and what the correct behavior should be.
    \item We gave the prompt to the LLM and got back the fixed code.
    \item We applied the fix and re-ran all tests to make sure nothing else broke.
\end{enumerate}

\textbf{LLM~1 fixes (2 bugs):}
\begin{itemize}
    \item Task~\#31 (\texttt{isPrime}): Changed \texttt{i * i <= n} to \texttt{(long) i * i <= n} to stop integer overflow.
    \item Task~\#45 (\texttt{triangleArea}): Changed \texttt{(a * h) / 2.0} to \texttt{a * (h / 2.0)} so the multiplication does not overflow first.
\end{itemize}

\textbf{LLM~2 fixes (4 bugs):}
\begin{itemize}
    \item Task~\#13 (\texttt{greatestCommonDivisor}): Added \texttt{Math.abs()} calls at the start to handle negative numbers.
    \item Task~\#25 (\texttt{factorize}): Changed the loop to only go up to $\sqrt{n}$ instead of $n$.
    \item Task~\#45 (\texttt{triangleArea}): Same fix as LLM~1.
    \item Task~\#49 (\texttt{modp}): Changed \texttt{int result = 1} to \texttt{int result = 1 \% p}.
\end{itemize}

\section{Phase 2: Integration Testing}
\label{sec:phase2}

\subsection{BookScan Class Generation}

In Phase~2, we created a Java class called \texttt{BookScan} whose primary purpose is to determine how many times words of a given length appear in a multi-line text and on which lines they appear. The class integrates three utility methods from Phase~1: \texttt{howManyTimes} (Task~\#18, overlapping substring counting), \texttt{strlen} (Task~\#23, string length), and \texttt{flipCase} (Task~\#27, case inversion).

We generated \texttt{BookScan} using both LLMs under two prompt conditions: (1)~an \textbf{unmodified \& combined} prompt that concatenated the raw HumanEval descriptions, and (2)~an \textbf{edited \& combined} prompt with improved clarity, specified return types, edge case requirements, and case-insensitive matching instructions. This produced four variants in total.

The edited prompts fixed all major bugs: LLM~1's case-sensitivity issue, LLM~2's null-pointer crashes, duplicate token counting, and missing punctuation stripping. The most impactful prompt changes were:

\begin{itemize}
    \item \textbf{Null handling:} Adding ``handle null inputs gracefully'' eliminated all null-related crashes in LLM~2.
    \item \textbf{Case insensitivity:} Specifying ``support case-insensitive matching using flipCase'' fixed LLM~1's case-sensitive word grouping.
    \item \textbf{Return type specification:} Requesting \texttt{Map<String, Map<String, Object>>} produced consistent APIs across both LLMs.
    \item \textbf{Processing pipeline:} Enumerating the five processing steps produced cleaner, more maintainable code.
\end{itemize}

Notably, the delta between unmodified and edited was \textbf{larger for Claude (LLM~2)} than for Gemini (LLM~1). Claude follows instructions literally---when given minimal prompts, it omits null guards and deduplication. Gemini proactively adds safety measures even without being asked, making it less sensitive to prompt quality.

\end{itemize}

\subsection{Integration Testing vs.\ Unit Testing Challenges}

Compared to the unit testing in Phase~1, integration testing of \texttt{BookScan} presented unique challenges:

\begin{enumerate}
    \item \textbf{Method interaction bugs:} The substring false-positive bug only manifests when \texttt{howManyTimes} is used within the scanning context (searching normalized lines), not when tested in isolation.
    \item \textbf{State accumulation:} The duplicate counting bug in LLM2 unmodified occurs because per-line occurrence counts are accumulated without deduplication---a pattern that wouldn't appear in unit tests of individual methods.
    \item \textbf{API design divergence:} Without prompt engineering, each LLM chose different method names, return types, and inner classes, making it harder to write standardized comparison tests.
    \item \textbf{Case normalization chains:} The edited versions chain \texttt{flipCase} through a helper method for normalization. If \texttt{flipCase} had a bug, it would cascade through all word matching---a failure mode absent from isolated unit tests.
\end{enumerate}

\section{Conclusion}
\label{sec:conclusion}

In this project we tested Gemini Pro (LLM~1) and Claude Opus~4.6 (LLM~2) across two phases: unit testing of 30 HumanEval tasks and integration testing of a \texttt{BookScan} text analysis class.

\textbf{Phase~1 findings:}
\begin{enumerate}
    \item Both LLMs wrote code that works correctly for normal inputs. All 30 tasks passed the base tests without any changes to the source code.
    \item After one round of test improvement, both LLMs got to 100\% branch coverage on all 30 tasks.
    \item But even with full coverage, manual testing found 2 bugs in LLM~1 and 4 bugs in LLM~2. All the bugs were in boundary conditions like overflow, missing input checks, slow algorithms, and wrong initial values.
    \item LLM~1 (Gemini) had fewer bugs (6.7\% vs.\ 13.3\%), so it wrote more reliable code for edge cases.
    \item Both LLMs were able to fix all the bugs when given detailed prompts with the failing test and the root cause.
\end{enumerate}

\textbf{Phase~2 findings:}
\begin{enumerate}
    \item Prompt engineering had a dramatic impact on code quality. Edited prompts eliminated all major bugs (case sensitivity, null crashes, duplicate counting, missing punctuation handling) in both LLMs.
    \item Claude (LLM~2) was more sensitive to prompt quality---the improvement from unmodified to edited was larger for Claude than for Gemini. Claude follows instructions literally, while Gemini proactively adds safety measures.
    \item Despite 95--100\% branch coverage, LLM-generated integration tests only covered 39.4\% of systematically identified equivalence classes and boundary values.
    \item Integration testing revealed bugs that unit testing could not: method interaction issues (substring false positives) and state accumulation bugs (duplicate counting) only manifest when methods are composed together.
\end{enumerate}

The overall takeaway is that LLMs are powerful tools for code and test generation, but they require both \textbf{careful prompt engineering} and \textbf{manual black-box testing} to produce reliable software. Branch coverage is a necessary but insufficient quality metric, and prompt quality significantly affects the reliability of generated code---especially for LLMs like Claude that follow instructions literally.
